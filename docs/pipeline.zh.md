# q-notes 编辑流程（中文版）

先保存原始材料，再决定是否展开；可以自己写，也可以请求有针对性的 AI 帮助。
先检查意思、思想归属与证据，再改文风，预览中英两版，最后明确批准发布。
保留私人片段、留下问题、暂时不出稿，都可以是正常结果。

本文对应 `docs/pipeline.md`；有冲突以英文版为准。材料与篇幅规则在
`docs/material-form.md`，独立审稿规则在 `docs/editorial-critic.md`。

## 1. 为什么调整

旧流程允许临近过期的未确认回答变成笔记，用旧文章和随手记补稿，并按稿龄自动
降级、关闭。这些规则已移除。保存一个想法不等于要求写文章，更不等于同意发布。

## 2. 设计原则

- 作者选材料，并明确要求起草，或亲自标记当前材料 `Ready to draft`，才可开始。
  检查后续撤回、修改、已有 PR 和已消费的授权，避免重复起稿。
- 未确认的回答保持原样；答完、临近过期、日历触发都不能授权起草短笔记。
- 可以直接写或粘贴完整稿，不必重新访谈。AI 可按需提一个问题、挑战一个观点、
  查证据或建议修改；明确要求时也可生成整稿。
- 原话和不确定性保留。模型建议不能自行变成作者立场。
- 不要求每周写作、五个问题、复述、A/B 练习、三句原话、标题或结尾练习。
- 不因稿龄自动降级、关闭或催促发布；成熟度标签不替代论证和作者认可。
- 此仓库、分支和 PR 可能公开；登录和 noindex 不提供 Git 隐私。私人材料不能
  为了留工作记录而复制到这里，存储边界由 #142 验证。

## 3. 内容形式

| 标签 | 合适的材料 | 篇幅 |
|---|---|---|
| `note` | 一个具体观察、场景、细节或值得留下的问题 | 英文通常不超过 700 词，无下限 |
| `essay` | 足以支持更长文章的具体材料 | 英文通常不超过 1,500 词，无下限 |
| `tracker` | 用新证据评估以前可检验的预测 | 按材料需要 |

个人写作可以靠细节、幽默或开放问题成立，不必附带理论、反方、分类、预测或总结。
中英文按含义核对，不设字数比例。成熟度字段暂时保留，但不充当提前发布的理由。

## 4. 作者主导的流程

### 4.1 可选发现 — Scout

01 可以推荐阅读或问题，不设候选数量、作者关联或发稿任务指标。旧文章只能提供
历史、比较或来源线索，不能单独授权当前立场。

### 4.2 可选提问 — Interviewer

02 从作者选择的材料出发，指出有意思的地方、关键缺口和一个有用问题。额外问题
按需提供。跳过不触发替代选题，保存答案不自动授权起草。

### 4.3 按请求起草 — Drafter

03 先核对意图和已有工作，再整理精简的 Author Kernel、Claim Ledger、Material Audit
与 Form decision。保留现有标题和 Cn/Hn ID 供客户端使用；引用同一份材料，避免重复
清单。写完后检查自然终点，保留真正改变论点的末段证据或反方，不按比例硬删。
先审思想归属、证据、标题和摘要的确定性，再润色。没有起草意图就不建内容 PR。

### 4.3b 独立审稿 — 编辑批评器

03b 编辑批评器只给一个精简结果，使用 `KEEP | CUT | DOWNGRADE | SPLIT | SKIP`。
按 `docs/editorial-critic.md` 检查具体主张的证据作用、推理缺口、文章主线、类比、
分类、标题摘要、反方、预测和自然终点。类比不能证明目标机制，相关文献不能补上
因果推理缺口。重组属于 CUT/SPLIT 的行动，不增加裁决类型。

语义改变需要重新独立审稿。纯机械修改只有确认不改变意思，才可延用 KEEP；
作者的发布批准仍在任何 head 修改后失效，需要重新预览。

### 4.4 待作者发布 — Ship gate

04 先处理作者反馈，要求当前适用的独立 KEEP，再检查材料、双语一致性、归属、
证据和标题摘要，最后改文风并运行机械检查和构建。保留当前 SHA 的 gate marker。
Ready 只表示可供作者审阅，不授权合并。两版正文、标题、摘要及公开元数据需一起
预览和批准；之后任何修改均需重看。服务端强制约束由 #141 实现。

### 4.5 可选维护 — Gardener

05 检查链接、生命周期与真实审稿失误，不考核篇数、Essay 比例或发布速度。
保留原始输入和已确认偏好；自动声纹学习、复述与逐篇校准暂缓。

## 5. 完成定义

私人片段或不出稿也能完成一次协助。准备发布则需有授权、足够材料、清楚的思想
归属、适用的独立 KEEP、中英含义与生命周期一致、机械检查和构建通过。
标题、摘要和社交描述的主张不能超出正文证据。最后仍需作者明确批准所预览版本。

## 6. 双语设计（中英双语）

### 编辑契约

每一篇发表作品都有英文版和中文版，写成**转创（transcreation）而非直译**。共同真相来源是 Claim Ledger，不是两篇文章共用同一种结构。

- **含义必须一致**：论点、必需主张、事实、数字/日期、来源支撑、因果方向、立场/不确定程度，以及成熟度/公开含义。
- **每种语言独立决定**：主张顺序、章节结构/顺序、标题及数量、段落边界、开头/结尾、连接骨架、长度。
- **不设硬长度比例**：检查的是 Claim coverage，不是词数/字数。
- **受词表约束**：复用术语按 `research/glossary.md`。

### 共享材料包，独立成文

在任一种语言开始写正文前，先冻结：

- Author Kernel；
- Claim Ledger；
- 来源链接与事实支撑；
- source-confidence/domain-limit；
- glossary 决定；
- Material Audit 与 Form decision。

先用作者原材料更偏向的语言自然起草。第二种语言从同一共享材料包 clean-room 成文，不照着第一版句子/章节顺序翻。两篇都存在后再按 Claim ID 做 parity。

结构恰好相同并不自动错误；过度整齐的 1:1 镜像只是一个值得检查的信号。

### 按 Claim ID 检查一致性

Parity 意味着：

- `Required in: EN + ZH` 的 claim 两边都有；
- 数字/日期一致；
- 来源支撑同一个事实；
- 因果方向不反转；
- 立场/不确定性等价；
- `Model-hypothesis` 不会只在一边悄悄变成已采纳立场。

不意味着 claim order、标题、段落、反驳位置、开头结尾、长度必须一致。

```md
## Bilingual parity

| ID | Claim | EN | ZH | Notes |
|---|---|---|---|---|
| C1 | <简短主张> | ✅ | ✅ | 中文先给结论，再补背景 |
| C2 | <简短主张> | ✅ | ✅ | 英文单独成段 |
```

证据例子两边保留，除非 ledger 明确标可选；纯修辞例子可以各自本地化，但不能增加事实、改变论点或虚构亲历。

### 内容模型（Phase 2，独立 PR）

目标：

1. `src/content.config.ts` 加 `lang: z.enum(['en', 'zh'])` 和 `translationKey`；
2. 文件变为 `<translationKey>.en.md` / `.zh.md`；
3. 英文 URL 保持 `/posts/<slug>`，中文 `/zh/posts/<slug>`；
4. 英/中各自 RSS；
5. 校验 CJK 排版；
6. 回填现有文章中文版。

Phase 2 之前，中文草稿继续停在 `drafts/zh/<slug>.md`，避免被英文 collection 意外发布。

## 7. 保存原始材料

保留中英混合、原话、疑问和未完成状态。作者没有要求起草时，不消费、不补全。
未经验证的公开 Git/PR 不能存放私人素材。现有记录保持可恢复。

## 8. 执行与调度边界

每次运行读取当前 `AGENTS.md`、`docs/pipeline.md` 和对应的 `automations/` 文件。
改提示词不会修改外部任务、部署 Worker 或取消已有日程。英文版 §8 列出完整清单：
GitHub Actions 只做 PR 检查；Wrangler 周二/周五 cron 仅发通知；旧 Flow 的截止日、
未确认 Note 提示与停滞提醒仍需后续修改。外部调度配置尚未在本次变更中验证。
上线前核查真实任务，替换粘贴的旧提示词并取消重复起草任务；不能声称已经完成。

## 9. 评估

使用 `tests/editorial/author-led-v1.md` 的冻结正反例，记录实际输出和问题。
测试无材料/无起草意图、过期前未确认答案、短观察、不支持的推论、过强标题摘要、
材料充足的技术稿。taste/map 三篇需核对原始输入和一手来源，旧文章或正例标签不能
证明作者采纳。代码测试和字符串检查不能证明编辑质量；完整独立评估与真实运行
验证仍需明确执行。没有篇数、长度或裁决比例指标。

## 10. 思想归属

写得像作者，不代表想法真的属于作者。更隐蔽的失败是：模型把旧立场当许可，补出新的机制、预测、框架，甚至虚构“我以前这么想，后来改变了”的心路历程。

> 允许 AI 帮忙把想法写清楚，不允许它替作者把没想完的地方想完。

这条规则管起草者（§4.3）、独立 critic（§4.3b）、发稿闸（§4.4）和园丁（§4.5）。

### Author Kernel

只从当前作者输入、`research/positions.md` 已采纳条目、或 `research/voice.md ## Stances` 明确晋升立场中建立。研究来源能支撑事实，但不能进入 `Explicit positions`。

严格 v1 下，**已发表文章正文只是历史/context**，不能单独授权当前 `Q-explicit`。

```md
## Author Kernel

### Explicit positions
-

### Concrete material
-

### Epistemic boundaries
-

### Unresolved doubts
-

### Characteristic wording worth preserving
- "..."
```

Kernel 不要被模型“整理得更完整”。“我不知道”“我只是猜”“这个问题还没想完”都是一等内容。

### Claim Ledger — 四类归属

```md
## Claim ledger

C1. <claim> — Q-explicit (interview Q1) — Required in: EN + ZH
C2. <claim> — External (<source>) — Required in: EN + ZH
C3. <optional item> — Q-derived (...) — Required in: optional
```

1. **`Q-explicit`**：当前作者输入、已采纳 `positions.md`、或已晋升 Stance 直接授权的立场。
2. **`Q-derived`**：极近的推论，不增加新的价值判断或因果理论。若一个理性读者可以接受 parent claim 却拒绝这个推论，它就不够近。
3. **`External`**：有来源的事实或明确归属给外部人的观点。
4. **`Model-hypothesis`**：模型新提出的机制、因果、框架、预测、分类、跨领域类比或“真正原因是……”重构。不能静默变成作者第一人称立场。删掉或明确写成可能性，并在 `## Candidate hypotheses — not yet yours` 里给 `Hn`。

Claim Ledger 同时是双语 parity 的真相来源。

### 不虚构作者心路历程

`I used to think... / I've come to think... / I changed my mind...` 等句子是关于作者历史的事实，不是文风。只有原始作者材料真的记录过这段变化时才允许。

### 采纳协议

作者在 PR 里回复：

```md
**Adopt hypothesis — H1**
```

或：

```md
**Reject hypothesis — H1**
```

采纳后记录直接进 `research/positions.md` 的 `main`；拒绝则从草稿移除，不进入 canon。采纳如果改变公开语义范围，发稿闸要判断是否需要新一轮 03b critic。

### 校准案例

- **PR #62**：软件亲历 + 明确硬件边界不应被补成完整跨领域 `consequence gate` 理论。预期 critic 为 `DOWNGRADE` 或 aggressive `CUT`。
- **PR #64**：保留 taste/judgment/decisiveness 的已挣到区分；pricing/compensation/2028 falsifier 若未单独挣到，应 cut/split/保持 hypothesis。
- **真实纠错**：作者明确说“我之前的定义错了”时，change-of-mind 是 `Q-explicit`。critic 应把真正的纠错/深化视为 self-novelty，而不是因为复用旧术语就处罚。

更完整的 #68 语义回归集合见 `tests/editorial/critic-v2.md`。
