多个编程 agent 的第一个实际失败，可能并不像坏代码。

它更可能像五个还不错的 pull request 同时出现。每一个单独看都合理，每一个都通过自己的测试，但没有一个知道其他几个也在改同一个仓库。

这已经不是"agent 会不会写代码"的问题。它更像空中交通管制。稀缺的工作变成了：哪个 agent 可以碰哪块代码，按什么顺序，允许制造多少合并成本，由谁负责。

代码审查仍然必要。但当自主贡献者开始重叠，审查本身不够了。一个有很多 agent 队友的代码库，需要交通管制。

## 数据正在从传闻走向碰撞

7 月 6 日的一篇关于 [GitHub 上 AI agent pull request](https://arxiv.org/abs/2607.04697) 的论文，是目前最清晰的信号。作者研究了 2,807 个仓库里的 33,596 个 agent 提交的 pull request。

在最严格的定义下，也就是两个 agent PR 在完全同一时间打开，40.2% 的仓库出现了共同活跃的 agent PR 对。这些共同活跃的 PR，占样本中所有 agent PR 的 79.4%。如果把协作窗口放宽到一周，仓库比例升到 53.4%，而 95% 的 agent PR 都和另一个 agent PR 同时活跃。

这很重要，因为并行 PR 不只是并行工作。它们是在修改同一个共享对象。

论文对 747 对共同活跃的 PR 重放了三方 git merge。同一个 agent 平台内部的 PR 对，文本冲突率是 19.8%。不同 agent 之间的 PR 对，冲突率是 41.7%。不同 agent 的组合并不多，只占完全重叠共同活跃 PR 对的 0.5%，但方向很有用：不同自动化工作者之间的干扰，可能比单一平台产生多个分支更尖锐。

这些冲突也不主要是 lockfile 噪音。论文说，84.4% 的冲突文件是源代码文件。接近 42% 的冲突是结构性的：一个分支删除了另一个分支修改的文件，或者两个分支各自新增了同名但内容不同的文件。

这才是有意思的地方。agent 不只是在争同几行代码。它们有时是在争一个东西到底应不应该存在。

## 局部正确不等于全局有序

我们习惯用一个问题审查软件变更：这个 PR 对不对？

agent 密集的软件工作，多了一个更早的问题：这个 PR 应不应该先于其他 PR 合并？

一个补丁可以单独正确，但在顺序上很昂贵。一个 agent 抽出 helper。另一个 agent 重写调用方。第三个 agent 按旧结构更新测试。第四个 agent 在一个马上要消失的文件里修日志。每个变化都说得过去。合在一起，就形成了一个没人真正设计过的合并队列。

这就是为什么 agent 产出看起来很高效，代码库却可能变得更难治理。问题不只是质量。问题是时机、所有权和影响面。

更大的生态证据也指向同一个方向。6 月的 [*Augmentation with Dilution*](https://arxiv.org/abs/2606.26289) 研究了 2023 年 1 月到 2026 年 5 月的 11,097 个 GitHub 仓库。它发现，引入 AI agent 后，人类贡献者密度下降，新人占比下降 3.7 个百分点，review 深度增加 5.3%。作者用的词很准确：带着稀释的增强。更多生成出来的工作，不自动意味着更多人类理解。

另一篇关于 [agent 日志行为](https://arxiv.org/abs/2604.09409) 的论文发现，在研究的仓库里，72.5% 的生成后日志修复是人类完成的。这是一种安静的维护劳动。PR 可能已经合并，但观测性决策还要由人类在事后清理。

把这些放在一起，模式很清楚：agent 把工作推到了 review 和集成层。瓶颈没有消失。它移动到了那些决定变更如何组合的人和系统身上。

## 代码库需要一个控制面

交通管制听起来很大，但实际版本很无聊。

agent 平台需要知道代码库里哪些区域已经被占用。一个任务开始改动前，应该先声明它要碰的范围。第二个任务如果也要碰同一块区域，应该在早期就看到冲突，而不是等两个 agent 都花完 token、做出漂亮分支之后才发现。

团队也需要合并顺序规则。重构分支通常应该先于依赖旧结构的功能分支合并。schema 变更应该有明确负责人和狭窄窗口。生成测试的任务应该知道，它正在测试的实现是否稳定，还是马上会被替换。

这不只是工具问题。它是一个被 git 暴露出来的管理问题。

必须有人判断，十个 agent PR 到底是十个独立改进，还是围绕一个没说清的目标乱转。必须有人杀掉重叠工作。必须有人说："这个 agent 可以更新测试，但不能创建新抽象。"必须有人注意到，代码库吸收活动的速度已经超过了吸收意图的速度。

这个人可以是 tech lead、code owner、产品工程师，也可以是经理。头衔不重要。功能才重要：在自主工作变成共享状态垃圾之前，把顺序安排好。

## 小 PR 不是全部答案

最明显的反驳是，软件团队早就有工具处理这些事。把 PR 做小一点。使用 merge queue。设置 code owner。用 feature flag。经常 rebase。让 CI 抓剩下的问题。

对，这些都有效。7 月 6 日的论文衡量的是文本冲突，不是构建冲突或语义冲突。所以不能把每一次冲突都当成产品失败。有些冲突很小。有些只是并行开发的普通成本。

但这不足以推翻这个判断。现有工具是围绕稀缺的人类贡献者设计的。人通常知道还有谁在做什么，至少可以被问到。agent 改变了尝试工作的速度。它也让一个人更容易同时发起多个分支，而这些分支之间的相互影响，未必有任何一个人完整想过。

merge queue 决定什么可以落地。agent 交通管制必须更早一步，决定什么应该同时被尝试。

这个区别很重要。如果两个 agent 都在改 onboarding，问题不只是 git 能不能合并文件。问题是代码库里是否出现了两套互相竞争的 onboarding 思路。如果一个 agent 删除 helper，另一个 agent 又基于它继续开发，问题不只是冲突标记。问题是没有任何一个工作者真正拥有架构方向。

## 有用的指标是避免了多少碰撞

下一代真正成熟的 agent 平台，不应该只炫耀 PR 数量。它应该展示避免了多少碰撞。

系统有多少次在分支发散之前发现重叠工作？有多少次让一个任务排在重构之后？有多少次因为两个 agent 想要不兼容的设计而要求人类决策？有多少 agent PR 是早早被杀掉的，而不是被打磨成 review 负担？

最后这个数字可能会成为成熟的信号。一个早早杀掉 agent 工作的团队，不是在浪费创造力。它是在拒绝把廉价行动转化成昂贵集成。

值得追踪的预测很简单：到 2027 年底，成熟的 agent 软件团队会把分支占用、合并排序和冲突预算当成一等产品基础设施。胜出的流程不会是"十个 agent，十个 PR，一个疲惫的 reviewer"。它会是一个代码库级别的调度器，知道什么时候正确答案不是再来一个补丁。

代码仍然必须写得好。但在有 agent 队友的世界里，顺序错误的好代码，也只是另一种混乱。
