编程 agent 写出的代码可能都不错，最后却还是把事情搞砸。

想象一下，五个 pull request 同时出现。每一个看起来都合理，也都通过了自己的测试。但这些 agent 不知道，其他 agent 也在改同一个代码库。

这会是团队大规模使用 agent 后遇到的下一个问题。写代码越来越便宜，但决定谁该改什么、先改什么，并没有变容易。

团队需要一套 *agent 交通管制*：明确哪个 agent 可以改哪部分代码，哪些工作要先做，重复的工作应该在什么时候停下来。

代码审查是在补丁写完以后找问题。交通管制应该更早，在互相冲突的补丁出现之前就把它们拦下来。

## 碰撞已经开始出现

7 月 6 日的一篇 [GitHub AI agent pull request 研究](https://arxiv.org/abs/2607.04697)，分析了 2,807 个仓库里的 33,596 个 agent PR。

作者先找出那些在同一时间处于打开状态的 agent PR。40.2% 的仓库里出现过这样的 PR 组合。样本中 79.4% 的 agent PR，都属于这些有时间重叠的组合。

如果把时间范围放宽到一周，53.4% 的仓库出现了重叠的 agent 工作。在这个范围里，95% 的 agent PR 都和另一个 agent PR 有重叠。

工作重叠不一定会产生冲突。但几个 agent 在没有共同计划的情况下修改同一个代码库，冲突的机会自然会增加。

论文还对 747 对同时打开的 PR 重新做了 git merge。来自同一个 agent 的 PR，文本冲突率是 19.8%。来自不同 agent 的 PR，冲突率是 41.7%。不过，后一组只占重叠 PR 的 0.5%，样本很小，现在还不能把这个差距看得太重。

冲突的类型更值得注意。84.4% 的冲突文件是源代码。接近 42% 的冲突改变了代码库的结构：一个分支删掉了另一个分支正在修改的文件，或者两个分支各自创建了不同版本的同名文件。

这些 agent 不只是在改同几行代码。它们有时连一个文件该不该存在都没有共识。

## 好补丁也可能来错顺序

我们审查软件变更时，通常会问：这个 PR 对不对？

多个 agent 同时工作时，团队还要先问一个问题：这项工作现在该不该开始？

一个 agent 抽出一个 helper。另一个重写调用它的代码。第三个按旧版本更新测试。第四个去修一个文件里的日志，而第一个 agent 正准备删掉这个文件。

每个补丁单独看可能都没问题。放在一起，却成了一团没人主动选择的麻烦。

所以，PR 数量多不一定代表效率高。问题不一定是代码质量，也可能是顺序不对、负责人不清楚，或者太多 agent 同时挤在同一块代码里。

另外两项研究也看到了类似的问题。[*Augmentation with Dilution*](https://arxiv.org/abs/2606.26289) 研究了 2023 年 1 月到 2026 年 5 月之间的 11,097 个 GitHub 仓库。团队采用 AI agent 以后，人类参与在整体工作中所占的比重下降。新人占比下降了 3.7 个百分点，每个 PR 得到的 review 增加了 5.3%。

代码产出更多了，但人的理解没有以同样的速度增加。

另一篇关于 [agent 如何写日志](https://arxiv.org/abs/2604.09409) 的论文发现，在生成代码加入仓库后，72.5% 的日志修复仍然由人完成。agent 交出了补丁，但很多日志选择还要靠人收拾。

Agent 没有消除审查和整合代码的工作。它只是把更多工作推到了这里。

## 交通管制具体怎么做

实际做法并不复杂。

一个 agent 开始工作前，应该先说明它准备改哪部分代码，想解决什么问题。如果另一个任务已经覆盖同一块区域，系统应该尽早提醒。人可以把两个任务合在一起，让其中一个排队，或者直接停掉一个。

有些工作也有明显的先后顺序。重构通常应该先合并，依赖旧结构的功能再跟上。数据库变更应该只有一个负责人。另一段实现马上要被替换时，就不该让 agent 继续为旧实现写测试。

工具可以发现重叠，但不能替人做所有决定。还是要有人负责安排工作顺序。

这个人可以是 tech lead、code owner、产品工程师，也可以是经理。头衔不重要。重要的是，不要让 agent 制造工作的速度，超过团队理解和整合这些工作的速度。

## 小 PR 还不够

团队已经有不少好用的办法：小 PR、merge queue、code owner、feature flag、经常 rebase，还有 CI。

这些办法都有用。7 月 6 日的论文只统计文本冲突，没有统计构建失败或产品问题。有些冲突可能很容易解决。并行开发本来就会产生 merge conflict。

但 agent 改变了新工作开始的速度。一个人现在可以同时启动几个分支，却未必先想清楚它们该怎么配合。

Merge queue 回答的是：“这个 PR 现在能不能合并？”Agent 交通管制问的是：“这两个任务一开始就应该同时做吗？”

后一个问题出现得更早，也更重要。两个 onboarding 补丁可能没有 merge conflict，却给产品带来两套不同的 onboarding 思路。一个 agent 可能删掉某个 helper，另一个却正在基于它开发新功能。Git 可以显示冲突，但不能替团队决定方向。

## 也要统计没有做的工作

Agent 平台不应该只统计自己创建了多少 PR。

它也应该告诉团队：有多少重叠工作在代码写出来之前就被发现了？有多少任务因为要等重构而排队？有多少次因为两个设计互相冲突，请人来做了决定？有多少 PR 被及时停掉，没有被打磨成新的 review 负担？

早点停掉 agent 的工作，可能正是系统管理得好的表现。便宜的代码如果带来昂贵的清理，就没有多少价值。

我的预测是：到 2027 年底，真正大规模使用编程 agent 的团队，会把任务归属、工作顺序和重叠修改的限制，放进日常开发流程。最好的流程不会是十个 agent 把十个 PR 扔给一个疲惫的 reviewer。它会知道什么时候应该等一等，什么时候应该合并任务，什么时候根本不该再写一个补丁。
