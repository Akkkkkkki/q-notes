编程 agent 可能每个都写得不错，事情最后还是砸了。

想象一下：五个 pull request 同时出现，每个看起来都合理，也都通过了自己的测试。但这些 agent 互相并不知道，大家都在改同一个代码库。

这会是团队大规模用 agent 之后的下一个难题。写代码越来越便宜，可"谁该改什么、先改什么"这件事，并没有跟着变便宜。

团队需要的是一套 *agent 交通管制*：哪个 agent 能动哪部分代码、什么先合、重复的活儿什么时候叫停，都得有明确的规则。代码审查是在补丁写完之后找问题，交通管制要做的是赶在互相冲突的补丁写出来之前，就把它们拦住。

## 碰撞已经开始出现

7 月 6 日有一篇研究 [GitHub 上 AI agent pull request](https://arxiv.org/abs/2607.04697) 的论文，分析了 2,807 个仓库里的 33,596 个 agent PR，重叠的程度相当惊人：40.2% 的仓库里出现过同一时刻同时打开的 agent PR，这些组合覆盖了样本里 79.4% 的 agent PR；把时间窗放宽到一周，53.4% 的仓库有重叠的 agent 工作，95% 的 agent PR 都和另一个有重叠。

重叠不一定就是冲突。但几个"工人"在没有共同计划的情况下改同一个代码库，冲突自然就多了。

作者还把 747 对同时打开的 PR 重新跑了一遍 git merge：同一个 agent 的 PR 组合，文本冲突率 19.8%；不同 agent 的组合，41.7%。不过后一组只占重叠组合的 0.5%，样本太小，这个差距我现在不敢太当真。

更值得看的是冲突的类型。84.4% 的冲突文件是源代码，接近 42% 的冲突动到了代码库的结构：一个分支删掉了另一个分支正在改的文件，或者两个分支各写了一个不同版本的同名文件。也就是说，这些 agent 争的有时候根本不是同几行代码，而是一个文件到底该不该存在。

## 好补丁也可能来错顺序

审查代码变更，我们通常问的是：这个 PR 对不对？可是多个 agent 同时干活的时候，还有个更早的问题：这个活儿现在就该开始吗？

一个 agent 抽出一个 helper，另一个在重写调用它的代码，第三个按旧版本补测试，第四个在修某个文件的日志，而第一个 agent 正打算把这个文件删掉。

每个补丁单独看都没毛病，合在一起就是一团没人选择过的麻烦。

所以 PR 数量多，不见得是好事。问题不一定出在代码质量上，也可能是顺序不对、没人负责，或者太多 agent 挤在同一块代码里。

另外两项研究也指向同一个方向。[*Augmentation with Dilution*](https://arxiv.org/abs/2606.26289) 分析了 2023 年 1 月到 2026 年 5 月的 11,097 个 GitHub 仓库：团队用上 AI agent 之后，人类参与在整体工作里的比重下降，新人占比掉了 3.7 个百分点，每个 PR 得到的 review 反而多了 5.3%。代码产出更多了，人的理解没跟上。还有一篇研究 [agent 怎么写日志](https://arxiv.org/abs/2604.09409) 的论文发现，生成代码进仓库之后，72.5% 的日志修复还是人做的。agent 把补丁交了，不少烂摊子还得人来收。

Agent 没有消灭审查和整合的工作，只是把更多的活儿推到了这里。

## 交通管制具体怎么做

实际做法说白了不复杂。agent 开工之前，先说清楚自己要改哪块代码、想达到什么结果；要是另一个任务已经覆盖了同一块地方，系统就尽早提醒，由人来决定是把两个任务合并、让一个排队，还是干脆停掉一个。

有些工作本来就有先后。重构通常该先合并，依赖旧结构的功能再跟上；数据库变更该只有一个负责人；另一段实现马上要被换掉的时候，就别再让 agent 给旧实现补测试了。

工具能发现重叠，但不能替人做所有决定，最后还是得有人对工作顺序负责。这个人可以是 tech lead、code owner、产品工程师，也可以是经理，头衔不重要。要紧的是别让 agent 制造工作的速度，超过团队理解和整合这些工作的速度。

## 小 PR 还不够

团队手里已经有不少好办法：小 PR、merge queue、code owner、feature flag、勤 rebase，再加上 CI。这些都有用。公平地说，7 月 6 日那篇论文统计的只是文本冲突，不是构建失败或产品 bug；有些冲突可能很好解决，并行开发本来也一直会产生 merge conflict。

但 agent 改变了新工作启动的速度。一个人现在可以同时开好几个分支，却未必想清楚了它们之间怎么配合。

Merge queue 回答的是"这个 PR 现在能不能合"，交通管制问的是"这两个任务当初就该同时开吗"。后一个问题来得更早，也更要命：两个 onboarding 补丁可以顺利合并，却给产品留下两套不同的 onboarding 思路；一个 agent 删掉某个 helper 的时候，另一个可能正在它上面盖新功能。Git 能给你看冲突，但方向得有人来定。

## 也要统计没有做的工作

Agent 平台不该只汇报自己开了多少 PR，还该告诉团队：有多少重叠工作在代码写出来之前就被发现了，有多少任务排队等过重构，有多少次两个互相冲突的设计被交给人来拍板，有多少 PR 被及时停掉、没被打磨成 reviewer 的新负担。

早点停掉 agent 的活儿，可能恰恰说明系统管得好。便宜的代码要是带来昂贵的清理，就不划算了。

我的预测，留给以后回头验证：到 2027 年底，认真大规模用编程 agent 的团队，会把任务归属、工作顺序和重叠修改的限制写进日常开发流程。最好的流程不会是十个 agent 往一个疲惫的 reviewer 那里扔十个 PR，它会知道什么时候该等、什么时候该合并任务、什么时候干脆别再写这个补丁。
