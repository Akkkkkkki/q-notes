编程智能体常常还没写出坏代码就已经失败了：它不知道这项工作该放在哪里。

资深工程师知道哪个模块负责某个功能、哪些测试定义了契约，也知道哪个目录看着相关其实不该碰。这些知识很多根本不在代码里，而在人脑、旧 pull request 和审查习惯里。智能体没有这段共同历史，仓库要是不把自己的结构摆出来，它就只能靠搜索结果和附近的文件去猜。

观点很简单：适合智能体工作的代码库，不是 prompt 更长的代码库，而是能让"该在哪里动手"一目了然的代码库。

## 更多上下文不等于地图

7 月 2 日修订的论文 [*How Much Static Structure Do Code Agents Need?*](https://arxiv.org/abs/2606.26979) 测了一个很实际的想法：给编程智能体提供简单的调用关系、继承关系和配置依赖信息，看看会怎样。

提升不算大，但有用。函数级定位提高了 2.2 个百分点，每次任务平均少了 1.6 轮交互，不同运行之间的结果也更稳定；在中型代码库上，Pass@1 提高了 3.4 个百分点，代价是输入 token 多了大约 10%。说白了，这张地图买到的主要是更少的无效动作。

这件事重要，是因为很多团队到现在还把智能体失败当成 prompt 问题：加指令、贴更多文件、让模型想久一点。这些办法可能有点用，但上下文窗口再大，也不会告诉智能体谁负责某个决策、哪项测试才是真正的契约。

智能体总改错文件的时候，问题可能出在代码库本身。

## 代码库就是界面

对人来说，好的代码库本来就像一个界面：命名、目录、模块边界、测试和架构记录，都在告诉你该看哪里、什么不该改。智能体让这个界面的缺口更扎眼，因为它们最容易栽的地方，恰恰是那些只有在团队里待了很久的人才懂的部分。

代码库地图不一定是什么新的可视化工具，它可以只是几组说得清的答案：哪个模块负责这个行为，谁会调用这个函数，哪项配置控制它，哪些测试定义了契约，哪份决策记录解释了取舍，谁该来审查这次修改。

这些都是普通的工程工作。智能体只是让这项工作的价值更容易被算出来。

## 计划和检查也是地图的一部分

论文 [*Spec Growth Engine*](https://arxiv.org/abs/2606.27045) 从规格的角度讨论了同一个问题。它认为智能体工作有两个风险：上下文太多，以及代码悄悄偏离原计划。它提出的系统只把机器可读规格里相关的那部分给智能体，代码和规格一旦分岔，就阻止合并。完整框架对大多数团队来说可能太重了，但核心想法本身站得住：智能体既要知道在哪里干活，也要知道这次修改被允许改变什么。

更大的技术任务里也有同样的规律。[Reboot](https://arxiv.org/abs/2606.27122) 是一个把 C 解释器翻译成安全 Rust 的系统，它把工作拆成完整、可测试的功能，仅这一点就让验证通过率比只用多智能体翻译高出 6 到 20 个百分点。[NOVA](https://arxiv.org/abs/2606.27243) 做的是工业推荐系统的架构工作：按风险分配任务，跑多层检查，记下智能体不该走的路，高风险的活儿交给人。在一项任务里，论文报告需要人盯着的时间减少了 13 倍，无声失败也比它的编程智能体基线更少。

系统各不相同，结论倒是一致：路线、边界和检查越明确，智能体的自主工作越可靠。

## 更好的模型仍然需要清楚的代码库

合理的反方观点是：模型会越来越会读代码库，自己建地图。它们能翻历史、跑测试，还能提问。代码库地图，也许只是给今天这些还不够强的智能体搭的临时脚手架。

更好的模型确实会需要更少的帮助，这没错。但优秀的工程师同样能在混乱的代码库里干活，我们照样记录所有权和架构，因为每次都重新推断太慢、结果不稳，还没法审查。这条规则对智能体一样成立。智能体在一次任务里建的地图是私有的、临时的；存在代码库里的地图，谁都能检查、改进和复用。

## 智能体就绪就是良好的工程实践

实际结论没有一款新智能体产品那么让人兴奋：团队把代码库变得更好懂，智能体的表现就会变好。清楚的模块所有权、小的垂直切片、契约测试、保持更新的架构记录、明确的依赖边界。这些工作对新来的工程师同样有帮助。一个行为在哪里、什么不能动、改完怎么验证，人和智能体都答不上来的话，说明代码库藏起了重要的工作知识。

我预计到 2027 年底，严肃的软件团队会更少把"智能体就绪"理解成写 prompt，更多理解成代码库质量。最能从编程智能体身上拿到好处的团队，靠的不会是最长的指令，而是让"负责任的修改"最容易找到位置的代码库。

最好的智能体界面，可能就是代码库本身。
