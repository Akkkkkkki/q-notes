编程智能体经常不是因为写错代码而失败。它们更早就失败了：不知道这项工作应该放在哪里。

资深工程师知道哪个模块负责某个功能、哪些测试定义了契约，也知道哪个目录看起来相关但其实不该碰。这些知识很多不在代码里，而在人脑、旧 pull request 和审查习惯里。

智能体没有这段共同历史。如果仓库没有说明自己的结构，它只能根据搜索结果和附近文件来猜。

观点很简单：适合智能体工作的代码库，不是 prompt 更长的代码库，而是能清楚说明应该在哪里工作的代码库。

## 更多上下文不等于地图

7 月 2 日修订的论文 [*How Much Static Structure Do Code Agents Need?*](https://arxiv.org/abs/2606.26979) 测试了一个实用想法。研究人员向编程智能体提供简单的调用关系、继承关系和配置依赖信息。

提升不算巨大，但很有用。函数级定位提高了 2.2 个百分点，每次任务平均减少 1.6 轮交互，不同运行之间的结果也更稳定。在中型代码库上，Pass@1 提高了 3.4 个百分点，代价是输入 token 增加约 10%。

这不是智能水平的大幅提升，而是减少了无效行动。

这很重要，因为很多团队仍然把智能体失败当成 prompt 问题。他们增加指令、贴入更多文件，或者让模型思考更久。这些方法可能有用，但更大的上下文窗口不会说明谁负责某个决策，也不会告诉智能体哪项测试才是真正的契约。

如果智能体总是修改错误的文件，问题可能在代码库本身。

## 代码库就是界面

对人类来说，好的代码库本来就像一个界面。命名、目录、模块边界、测试和架构记录会说明应该看哪里，以及什么不该改。

智能体让这个界面的缺口更明显。系统中有些部分，只有在团队里待了很久的人才能理解，智能体在这些地方最容易出错。

代码库地图不一定是一套新的可视化工具。它可以只是几组明确的答案：

1. 哪个模块负责这个行为？
2. 谁会调用这个函数？
3. 哪项配置控制它？
4. 哪些测试定义了契约？
5. 哪份决策记录解释了取舍？
6. 谁应该审查这次修改？

这些都是普通的工程工作。智能体只是让这项工作的价值更容易衡量。

## 计划和检查也是地图的一部分

论文 [*Spec Growth Engine*](https://arxiv.org/abs/2606.27045) 从规格的角度讨论了同一个问题。它认为智能体工作有两个风险：上下文过多，以及代码悄悄偏离原计划。它提出的系统只向智能体提供机器可读规格中的相关部分，并在代码与规格分离时阻止合并。

完整框架可能超过大多数团队的需要，但核心观点已经足够：智能体既需要知道在哪里工作，也需要知道这次修改可以改变什么。

同样的规律也出现在更大的技术任务里。[Reboot](https://arxiv.org/abs/2606.27122) 是一个把 C 解释器翻译成安全 Rust 的系统。它把工作拆成完整、可测试的功能。与只使用多智能体翻译相比，这种方法让验证通过率提高了 6 到 20 个百分点。

[NOVA](https://arxiv.org/abs/2606.27243) 用于工业推荐系统的架构工作。它按风险分配任务，运行多层检查，记录智能体不该走的路径，并把高风险工作交给人。在一项任务中，论文报告需要人类参与的时间减少了 13 倍，同时相较其编程智能体基线减少了无声失败。

这些系统并不相同，但结论一致：路线、限制和检查越明确，智能体的自主工作越可靠。

## 更好的模型仍然需要清楚的代码库

合理的反方观点是，模型会越来越擅长阅读代码库并自己建立地图。它们可以检查历史、运行测试，也可以提问。代码库地图也许只是对今天较弱模型的临时帮助。

更好的模型确实会需要更少帮助。但这不是让结构继续隐藏的理由。

优秀工程师也能处理混乱的代码库。我们仍然记录所有权和架构，因为每次都重新推断很慢，结果也不稳定，而且难以审查。这个原则同样适用于智能体。

智能体在一次任务中建立的地图是私有和临时的。保存在代码库里的地图可以被所有人检查、改进和复用。

## 智能体就绪就是良好的工程实践

实际结论没有新智能体产品那么吸引人。团队可以通过改善代码库来提高智能体表现：清楚的模块所有权、小型垂直切片、契约测试、保持更新的架构记录，以及明确的依赖边界。

这些工作也会帮助新工程师。如果人或智能体不能快速回答一个行为在哪里、什么不能改变，以及如何验证修改，说明代码库隐藏了重要的工作知识。

我预计到 2027 年底，严肃的软件团队会更少把"智能体就绪"理解为 prompt 写作，更多把它理解为代码库质量。最能从编程智能体中获益的团队，不会拥有最长的指令，而会拥有最容易找到正确修改位置的代码库。

最好的智能体界面，可能就是代码库本身。
